# Changelog

## Open questions

- **Demonstrations and road closures: OK to use these two sources?** (2026-11-22) Both are official, neither has an open licence. (a) Berlin's list of registered assemblies (Polizei Berlin, LPD St 6) has a JSON export and is listed in Berlin's open-data register, but with the licence "other-closed / see website". It has about 50 entries a day, most of them small vigils without a route. (b) The Autobahn GmbH API (`verkehr.autobahn.de/o/autobahn`, the one behind the Autobahn app) is public but has no published terms; its traffic warnings (accidents, jams) are partly from INRIX, a commercial data provider ("source": "inrix"), while closures and roadworks are Autobahn GmbH's own. Options: (1) build both now, as with the Polizei Berlin press releases: facts only (date, time, place, route; never the topic's wording or the organiser), a link back, an `off` switch each; Berlin: only marches with a route (Aufzüge) and within about 1 km of a person or saved place; Autobahn: only full closures and accidents with a full closure, only Autobahn GmbH's own messages, never INRIX; (2) first ask Polizei Berlin and Autobahn GmbH (kontakt@autobahn.de) by email; (3) Autobahn only through the official Mobilithek (DATEX II, needs a free registration and a usage agreement). I'd go with (2) for Berlin and (3) for the Autobahn, and (1) only if you're comfortable with it. Roadmap "New topic: demonstrations, big events and road closures" waits for this.

- **Police in München, Augsburg, Leipzig, Dresden: ask for a feed?** (2026-11-22) Bavaria's and Saxony's police publish their press releases only as web pages, with no RSS or API (polizei.bayern.de loads them by JavaScript, `/rss/` answers 403; polizei.sachsen.de has an HTML list). Options: (1) ask both press offices (Polizeipräsidium München, Polizei Sachsen) whether an app may read their press releases and whether there's a feed; (2) read the HTML pages anyway (works, but fragile and without permission); (3) leave them out; the NINA police channel still brings their official warnings. I'd go with (1), and (3) until there's an answer. Roadmap "More crime coverage, part 2b" waits for this.

- **Cyber warnings for ordinary people: which ones?** (2026-11-20) BSI's public advisory feed (CERT-Bund WID) lists dozens of technical notices a day ("Schwachstelle in …"). Pushing those would be noisy and alarming. Options: (1) only "critical" notices for a short list of products most people have (iPhone/iOS, Android, Windows, Chrome, Firefox, Safari, WhatsApp), feed only, with "please update" as the advice; (2) only the BSI's own consumer warnings (Verbraucherschutz / Bürger-CERT), if they have a feed; (3) wait and do outages only. I'd go with (1), feed only, never a push. Roadmap "technology, part 5" waits for this; part 4 (CISA) is blocked because CISA's feeds can't be reached from the agent's sandbox.

- **Tech outages for mobile carriers and big banks: which source?** (2026-11-20) Verizon, AT&T, T-Mobile, Chase, Bank of America and Wells Fargo publish no public status API. Options: (1) FCC's Disaster Information Reporting System, public only when the FCC activates it for a disaster, so it misses everyday outages; (2) a licensed outage-data feed such as Downdetector (Ookla) — paid, but it covers carriers and banks in the US, Germany and India; (3) leave them out and rely on the services that do publish (15 today). I'd go with (3) now and look at (2) once there is budget. Roadmap "technology, part 3b" waits for this.

- **BVG/VBB disruptions: which data access?** (2026-11-18) There's no open, documented source I can build on. Options: (1) apply for VBB's official API (HAFAS, includes disruption messages; it's on the "Needs a human" list as "VBB API access"); (2) ask BVG for permission to use the disruptions JSON their website loads (`bvg.de/disruption-reports-service/…`), which has no published terms; (3) use S-Bahn Berlin / VBB disruption RSS if they offer one. I'd go with (1) for the long run and (2) as a quick start if BVG agrees. Until then the item stays open and the other sources run.

- **Sign in with Apple / Google, part 1: the server** (roadmap "Sign-in: Apple + Google", split into the server part, done, and part 2, the buttons in the phone app and web) [PRD 5.3, 7.1].
  - What it does: the app will send the identity token it gets from Apple's or Google's sign-in sheet to `POST /v1/auth/apple` or `POST /v1/auth/google`. The server checks it (`server/src/identity.ts`, no SDK, no new dependency): signature against the provider's published keys (cached; a new key is picked up by itself, with at most one fetch a minute), issuer, audience = our own client ids, expiry (60 s slack). It keeps only the provider's user id and the email; names and photos are ignored.
  - Same accounts as the email code: a known Apple/Google id signs in to its account (a new phone gets its places and settings back, as with the code). Otherwise, if Apple/Google has verified the email address, it joins the account with that email, or makes a new one. An unverified email never links (`400 email_required`), and an account already linked to one Google id never gets a second (`409 account_conflict`), so nobody can take over an account with someone else's address. Apple's "hide my email" relay addresses work; they become the account's email.
  - Data: new table `account_identities` (provider, provider user id → account; Postgres migration 12, SQLite schema, included in the SQLite → Postgres copy tool). I used a table instead of the `apple_sub` / `google_sub` columns the roadmap named: it needs no column change on existing SQLite files, and a third provider would need no migration. Deleting the account (GDPR) removes the link too.
  - Settings: `APPLE_CLIENT_IDS` (iOS bundle id `de.heyokay.app`, plus the web Services ID), `GOOGLE_CLIENT_IDS` (iOS, Android and web OAuth client ids), comma-separated. Unset → that route answers `503 provider_not_configured`, which is how it ships today. A bad token is `400 invalid_token` (not 401, so the app never mistakes it for a lost device token); Apple's or Google's key server unreachable is `503 provider_unavailable` (logged, goes to Sentry).
  - Not yet: no buttons (part 2), and no nonce check; part 2 adds the nonce together with the buttons, since the app creates it. Tokens only live minutes, so the risk until then is small and nothing is switched on anyway.
  - To check against the live services: the key URLs (`appleid.apple.com/auth/keys`, `www.googleapis.com/oauth2/v3/certs`) and claims follow Apple's and Google's documentation; the tests use a local key server with real RSA keys. The first real sign-in after the client ids are set is the live check.

# Changelog

## Open questions

- **Analytics: anonymous counts without asking, and which provider later?** (2026-11-24) The new app events (onboarding screens, permission answers, notifications switched off) go only to our own server and are kept as counts per day, platform and event name: no id, no IP, nothing stored for it on the device. My reading is that this isn't personal data, so it needs no consent and has no switch. Options: (1) keep it like that; (2) add a switch "Anonyme Nutzungsstatistik" under Settings → Privacy anyway (on by default), for people who want none at all; (3) ask at onboarding (off by default), which would hide exactly the drop-offs the funnel is for. I'd go with (1), or (2) if the DPIA prefers it; please check with whoever does the DPIA. Decision 9 (Mixpanel / Amplitude / Firebase / Matomo / PostHog EU) is still open: any of them would be one more provider in `lib/analytics.ts`, and one that tracks people individually needs a consent switch first.

- **How long to keep the decision log?** (2026-11-23) The new decision log (one row per pipeline step and Alert Desk action, no personal data) grows by a few rows per source item. Options: (1) 6 months, the minimum the EU AI Act sets for logs of high-risk systems, in case Hey-Okay is classified that way (the DPIA / AI Act classification is still under "Needs a human"); (2) 12 months, so a whole year of reviews can be audited; (3) as long as the events it describes (30 days), which is too short to audit anything. I'd go with (2) until the AI Act classification says otherwise. The roadmap item "Data retention" will use your answer; until then nothing is deleted.

- **Police in München, Augsburg, Leipzig, Dresden: ask for a feed?** (2026-11-22) Bavaria's and Saxony's police publish their press releases only as web pages, with no RSS or API (polizei.bayern.de loads them by JavaScript, `/rss/` answers 403; polizei.sachsen.de has an HTML list). Options: (1) ask both press offices (Polizeipräsidium München, Polizei Sachsen) whether an app may read their press releases and whether there's a feed; (2) read the HTML pages anyway (works, but fragile and without permission); (3) leave them out; the NINA police channel still brings their official warnings. I'd go with (1), and (3) until there's an answer. Roadmap "More crime coverage, part 2b" waits for this.

- **Cyber warnings for ordinary people: which ones?** (2026-11-20) BSI's public advisory feed (CERT-Bund WID) lists dozens of technical notices a day ("Schwachstelle in …"). Pushing those would be noisy and alarming. Options: (1) only "critical" notices for a short list of products most people have (iPhone/iOS, Android, Windows, Chrome, Firefox, Safari, WhatsApp), feed only, with "please update" as the advice; (2) only the BSI's own consumer warnings (Verbraucherschutz / Bürger-CERT), if they have a feed; (3) wait and do outages only. I'd go with (1), feed only, never a push. Roadmap "technology, part 5" waits for this; part 4 (CISA) is blocked because CISA's feeds can't be reached from the agent's sandbox.

- **Tech outages for mobile carriers and big banks: which source?** (2026-11-20) Verizon, AT&T, T-Mobile, Chase, Bank of America and Wells Fargo publish no public status API. Options: (1) FCC's Disaster Information Reporting System, public only when the FCC activates it for a disaster, so it misses everyday outages; (2) a licensed outage-data feed such as Downdetector (Ookla) — paid, but it covers carriers and banks in the US, Germany and India; (3) leave them out and rely on the services that do publish (15 today). I'd go with (3) now and look at (2) once there is budget. Roadmap "technology, part 3b" waits for this.

- **BVG/VBB disruptions: which data access?** (2026-11-18) There's no open, documented source I can build on. Options: (1) apply for VBB's official API (HAFAS, includes disruption messages; it's on the "Needs a human" list as "VBB API access"); (2) ask BVG for permission to use the disruptions JSON their website loads (`bvg.de/disruption-reports-service/…`), which has no published terms; (3) use S-Bahn Berlin / VBB disruption RSS if they offer one. I'd go with (1) for the long run and (2) as a quick start if BVG agrees. Until then the item stays open and the other sources run.

- **API hardening** (roadmap "API hardening") [PRD 11].
  - Rate limits: at most 300 requests a minute from one address and 120 a minute with one device token (`RATE_LIMIT_IP_PER_MIN`, `RATE_LIMIT_TOKEN_PER_MIN`, 0 switches one off); above that the answer is 429 with `Retry-After`. `/health` is never limited. A phone sends a location every few minutes and loads the feed now and then, so normal use stays far below. Kept in memory per machine.
  - The client's address: behind Fly every request seemed to come from Fly's proxy, so the existing sign-in lock and app-event limit counted everyone together. Now the address comes from the `Fly-Client-IP` header that Fly's edge sets, but only when the server runs on Fly (`FLY_APP_NAME` present) or `CLIENT_IP_HEADER` names a header; otherwise the connection's address, so nobody can choose their own address by sending that header.
  - Request bodies: at most 64 KB (the biggest real one is a few KB), else 413.
  - Security headers on every answer: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, HSTS (one year), a `Permissions-Policy` that switches off camera, microphone, location and payment, and a Content-Security-Policy that allows nothing for JSON answers. The Alert Desk page gets its own CSP: only its inline script and styles and calls to its own server. Personal answers (`/v1/me…`, alerts, sign-in) and all desk answers carry `Cache-Control: no-store`. CORS for the web app is unchanged.
  - Fuzz test: every route in `api.ts` (found by reading the file, so new routes are covered automatically) gets 25 requests with junk: random JSON (wrong types, huge numbers, long strings, nested objects, `__proto__`), broken JSON, junk query strings and ids, with and without device token, admin token or a made-up desk cookie. About 1 150 requests; none may answer 500 or log an error, and the test checks that 200, 400, 401 and 404 all occurred, so it really reached the routes. It found nothing to fix.
  - No new dependency.
  - Tests: `server/test/hardening.test.ts` (7 new: rate counter windows; headers and desk CSP, no-store, CORS preflight still 204; 64 KB limit; per-address limit with Retry-After, health exempt, next minute; per-token limit; client address only from the configured header, and the config default on Fly; the fuzz run).
